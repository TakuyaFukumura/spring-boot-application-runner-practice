## 2. 背景と目的

現在のリポジトリは、Spring Boot の `ApplicationRunner` による起動後処理、コマンドライン引数の解析、複数 Runner の実行順序を学ぶための小さなコンソールアプリケーションである。

本改修では、`ApplicationRunner` を「アプリケーションを起動するアダプター」として位置付け、Runner から業務処理を分離する。小さく完結するドメインを題材に、DDD（Domain-Driven Design）の設計思想をコードとテストから学べるリポジトリへ発展させる。

### 2.1 到達目標

- `ApplicationRunner` が起動処理の入口であり、業務知識を持たないことを理解できる。
- Application 層、Domain 層、Infrastructure 層の責務と依存方向を説明できる。
- Entity、Value Object、Repository、Domain Service、Application Service の使い分けをコードで確認できる。
- CLI 引数の変換・入力検証・ユースケース実行・結果出力を分離できる。
- ドメインロジックを Spring コンテキストや外部 I/O なしでテストできる。

## 3. 対象範囲

### 3.1 対象

- Spring Boot のコンソールアプリケーション
- `ApplicationRunner` を利用した一回限りのユースケース実行
- DDD の基本要素を使った最小限の業務モデル
- CLI 引数によるユースケースの選択と入力
- インメモリ実装による Repository
- 単体テスト、アプリケーション層テスト、起動テスト
- 学習順序と設計意図を説明する README・補助資料

### 3.2 対象外

- Web API、画面、認証・認可
- 本番向けの永続化製品や外部メッセージング基盤
- 複数サービスにまたがる分散トランザクション
- 完全な業務システムとしての網羅的な機能実装
- DDD のすべてのパターン（仕様書、ACL、イベントソーシング等）の実装

## 4. 想定する学習題材

題材は「注文（Order）の受付」とする。注文は CLI から受け付け、ドメインルールを満たす場合だけ登録する。題材は DDD の要素を説明できる程度に小さく保ち、フレームワークの設定よりも責務分離に焦点を当てる。

### 4.1 用語

| 用語 | 意味 |
| --- | --- |
| 注文 | 商品明細を持ち、受付状態を管理する集約 |
| 注文ID | 注文を一意に識別する Value Object |
| 注文明細 | 商品と数量を表す Value Object または Entity |
| 注文受付 | CLI から入力を受け、注文を作成・保存するユースケース |
| 注文一覧 | 保存済み注文を読み込み、結果を出力するユースケース |

### 4.2 初期ドメインルール

- 注文IDは空であってはならない。
- 注文明細は1注文につきちょうど1件とする。
- 商品名は空であってはならない。
- 数量は1以上でなければならない。
- 受付済みの注文は、同じ注文IDで二重登録できない。
- ドメインルール違反はドメインまたはアプリケーションの明示的な例外として扱う。

## 5. システム構成要件

### 5.1 レイヤー構成

```text
ApplicationRunner
    ↓
Application 層（ユースケース、入力・出力のDTO）
    ↓
Domain 層（Entity、Value Object、Repositoryの抽象、ドメインルール）
    ↑
Infrastructure 層（Repositoryのインメモリ実装、CLI出力など）
```

- `ApplicationRunner` は Spring Boot の起動ライフサイクルと CLI 引数の受け取りだけを担当する。
- Application 層はユースケースの手順を調整するが、ドメインルールを直接持たない。
- Domain 層は Spring の具象クラスや CLI に依存しない。
- Infrastructure 層は Domain 層が定義した抽象へ依存し、具象実装を提供する。
- 依存方向は、外側の層から内側の層へ向かう形を基本とする。

### 5.2 パッケージ方針

学習時に責務を追いやすいよう、次のパッケージ分割を基本とする。

```text
com.example.applicationrunner
├── ApplicationRunnerPracticeApplication
├── presentation
│   └── ApplicationRunner 実装
├── application
│   ├── usecase
│   └── dto
├── domain
│   ├── model
│   ├── repository
│   └── service
└── infrastructure
    └── repository
```

実装上の都合でクラス数を抑える場合も、パッケージ境界が示す責務は維持する。

## 6. 機能要件

### FR-01: ApplicationRunner による起動

- Spring Boot 起動後に `ApplicationRunner` が1回だけ実行されること。
- Runner は `ApplicationArguments` を受け取り、入力をアプリケーション層へ渡すこと。
- Runner は Entity の生成、Repository の操作、ドメインルールの判定を直接行わないこと。
- 複数 Runner を利用する場合は `@Order` で順序を明示し、学習資料で理由を説明すること。

### FR-02: 注文受付ユースケース

- CLI はサブコマンド形式とし、最初の通常引数で実行するユースケースを指定できること。
- 注文受付は `register` サブコマンドで実行できること。
- 注文一覧は `list` サブコマンドで実行できること。
- `register` 実行時に、注文ID、商品名、数量をオプション引数から受け取れること。
- 入力を DTO またはコマンドへ変換して Application Service に渡せること。
- Application Service がドメインモデルを生成し、Repository を通して保存すること。
- 正常終了時の受付結果を標準出力へ出力すること。
- 同一注文IDや不正な数量などを明示的なエラーとして扱うこと。

実行例:

```powershell
# 注文を登録する
.\mvnw.cmd spring-boot:run "-Dspring-boot.run.arguments=register --order-id=1001 --product=Book --quantity=2"

# 注文を一覧表示する
.\mvnw.cmd spring-boot:run "-Dspring-boot.run.arguments=list"
```

`ApplicationRunner` は `ApplicationArguments#getNonOptionArgs()` からサブコマンドを取得し、
入力の解釈とユースケースの選択を Application 層へ委譲する。Runner 自身は
`register` や `list` に対応する業務処理を持たない。

### FR-03: 注文一覧ユースケース

- 保存済みの注文を Repository から取得できること。
- 一覧取得の結果を、ドメインモデルそのものではなく出力用の形式へ変換して標準出力へ表示すること。
- 注文が存在しない場合も、成功・空結果の違いが分かる出力にすること。

### FR-04: 終了コード

- 正常終了時は終了コード `0` とすること。
- 入力不正、ドメインルール違反、ユースケース失敗時は終了コード `1` とすること。
- エラーの原因がログから追跡できること。
- 終了処理の責務をエントリーポイントまたは専用の終了コード連携に集約すること。

### FR-05: Repository の差し替え

- Domain 層に Repository のインターフェースを定義すること。
- Infrastructure 層にインメモリ実装を用意すること。
- インメモリRepositoryのデータはプロセス終了時に破棄し、複数回の起動をまたいで保持しないこと。
- Application 層のテストでは、Repository をモックまたはテスト用実装に差し替えられること。
- 将来の DB 実装を想定しても、ユースケースのコードを変更せずに差し替えられる設計とすること。

## 7. 非機能要件

### NFR-01: 可読性・学習容易性

- 各クラスの責務がクラス名とパッケージから推測できること。
- DDD 用語を導入する場合、README または補助資料に短い説明を加えること。
- 1つのクラスに CLI、ユースケース、ドメインルール、永続化の責務を混在させないこと。

### NFR-02: テスト容易性

- Value Object と Entity のドメインルールは Spring を起動せずにテストできること。
- Application Service は依存を差し替えてユースケース単位でテストできること。
- 少なくとも正常系、入力不正、ドメインルール違反、重複登録をテストすること。

### NFR-03: 既存学習内容の維持

- `ApplicationRunner`、`ApplicationArguments`、`@Order` の既存学習内容を失わせないこと。
- 既存の引数処理を全面的に隠蔽せず、Spring Boot が引数を解析して Runner に渡す流れを確認できること。
- Java と Spring Boot のバージョンは、特別な理由がない限り現行設定を維持すること。

### NFR-04: 実行再現性

- Maven Wrapper だけでビルド・テスト・実行確認ができること。
- README に正常系と異常系の実行例を記載すること。
- テストが実行順序やローカル環境の状態に依存しないこと。

## 8. テスト要件

| レベル | 対象 | 必須確認 |
| --- | --- | --- |
| Domain 単体テスト | Value Object、Entity、Domain Service | ルール違反を拒否し、正常な状態を生成できる |
| Application 単体テスト | 注文受付・一覧ユースケース | Repository と出力を差し替えて手順を検証できる |
| Runner 統合テスト | `ApplicationRunner` と Spring Context | 起動後に1回実行され、正しいユースケースが呼ばれる |
| 起動確認 | 実行可能 JAR または `spring-boot:run` | 正常系・異常系の終了コードと出力を確認できる |

## 9. 学習ステップ

1. 現状の `ApplicationRunner` と `ApplicationArguments` の動作を確認する。
2. Runner から Application Service へ処理を委譲する。
3. 注文ID・商品名・数量を Value Object として表現する。
4. 注文 Entity とドメインルールを実装する。
5. Repository の抽象とインメモリ実装を分離する。
6. 注文受付・注文一覧のユースケースを追加する。
7. CLI 入力、終了コード、テスト、README を整備する。
8. 依存方向と責務分離をコードリーディング補助資料へ反映する。

各ステップは、変更前後の差分とテスト結果を確認できる大きさに保つ。

## 12. 決定事項と未決事項

### 12.1 決定事項

- CLI の入力形式はサブコマンド形式とする。
- 初期サブコマンドは `register`（注文受付）と `list`（注文一覧）とする。
- サブコマンドは通常引数、各ユースケースの入力値はオプション引数として表現する。
- 初期実装では、1注文につき注文明細を1件に限定する。
- 複数明細への対応は、基本的な責務分離を学習した後の拡張候補とする。
- Repository はインメモリ実装とし、データは1プロセス内だけ保持する。
- ファイルやデータベースへの永続化は、Repository差し替えの発展課題とする。
- 初期実装ではDomain Eventを導入せず、基本的なドメインモデルとユースケースに集中する。
- Domain Eventは、基本構造を理解した後の発展課題とする。
- 業務結果は標準出力へ、診断情報とエラーはログへ出力する。
- 標準出力は他のコマンドやスクリプトから扱える形式を意識し、ログとは混在させない。

### 12.2 未決事項

現時点で未決事項はない。追加の論点が生じた場合は、実装開始前に本書へ追記して合意する。

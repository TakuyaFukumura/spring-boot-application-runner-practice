# コードリーディング補助資料

## 1. このプロジェクトの目的

このプロジェクトは、Spring Boot の `ApplicationRunner` を使って、アプリケーション起動後に一度だけ実行される処理を確認するための小さなコンソールアプリケーションです。

主な学習対象は次のとおりです。

- `ApplicationContext` の初期化後に実行される `ApplicationRunner`
- `ApplicationArguments` によるコマンドライン引数の読み取り
- 複数の Runner の実行順序を制御する `@Order`
- Runner と引数処理サービスを分離する設計
- 起動処理の成否をプロセス終了コードへ反映する方法

## 2. 全体像

アプリケーションの処理は、次の流れで進みます。

```text
main(args)
  |
  v
SpringApplication.run(...)
  |
  +-- ApplicationContext を初期化
  |     |
  |     +-- StartupOrderRunner.run(...)       @Order(1)
  |     |
  |     +-- CommandLineArgumentsRunner.run(...) @Order(2)
  |             |
  |             +-- CommandLineArgumentsProcessor.process(...)
  |
  +-- SpringApplication.exit(context)
  |
  +-- System.exit(終了コード)
```

`SpringApplication.run` は、Bean の準備と `ApplicationContext` の初期化を行います。初期化が完了すると、登録されている `ApplicationRunner` が実行されます。Runner の処理が終わった後、`main` は Spring の終了処理を呼び出し、プロセスを終了します。

## 3. 読む順番

コードを読むときは、次の順番にすると起動から引数処理まで追いやすくなります。

1. `ApplicationRunnerPracticeApplication`
2. `StartupOrderRunner`
3. `CommandLineArgumentsRunner`
4. `CommandLineArgumentsProcessor`
5. テストクラス

最初にエントリーポイントを確認し、次に Runner の実行順序を確認します。その後、引数を実際に処理するクラスへ進むと、責務の分離が分かりやすくなります。

## 4. クラスごとの責務

### `ApplicationRunnerPracticeApplication`

場所: `src/main/java/com/example/applicationrunner/ApplicationRunnerPracticeApplication.java`

`@SpringBootApplication` が付いたアプリケーションのエントリーポイントです。このアノテーションにより、コンポーネントスキャンと Spring Boot の自動設定が有効になります。

```java
var context = SpringApplication.run(ApplicationRunnerPracticeApplication.class, args);
System.exit(SpringApplication.exit(context));
```

ここで注目する点は次のとおりです。

- `SpringApplication.run` に元のコマンドライン引数を渡している
- `ApplicationContext` の初期化完了後に Runner が実行される
- 正常終了時は `SpringApplication.exit` の終了コードを `System.exit` に渡す
- `IllegalArgumentException` または `IllegalStateException` が発生した場合はログを出力し、終了コード `1` で終了する

つまり、`main` は起動と終了の制御を担当し、業務的な引数処理は担当しません。

### `StartupOrderRunner`

場所: `src/main/java/com/example/applicationrunner/StartupOrderRunner.java`

最初に実行される Runner です。

```java
@Component
@Order(1)
public class StartupOrderRunner implements ApplicationRunner
```

`@Component` によって Spring Bean として登録され、`@Order(1)` によって Runner の中で先に実行されます。処理内容は起動順序を示すログの出力だけです。

このクラスは、複数の Runner が存在する場合に `@Order` がどのように働くかを確認するためのサンプルです。

### `CommandLineArgumentsRunner`

場所: `src/main/java/com/example/applicationrunner/CommandLineArgumentsRunner.java`

Spring Boot が解析した `ApplicationArguments` を受け取り、プロセッサーへ渡す Runner です。

```java
@Component
@Order(2)
public class CommandLineArgumentsRunner implements ApplicationRunner
```

このクラスの責務は、起動タイミングで処理を開始することです。引数の検証やログ出力の詳細は `CommandLineArgumentsProcessor` に委譲しています。

コンストラクターで `CommandLineArgumentsProcessor` を受け取っているため、依存関係が明示されています。テストではプロセッサーをモックに置き換え、Runner が一度だけ呼び出すことを確認できます。

### `CommandLineArgumentsProcessor`

場所: `src/main/java/com/example/applicationrunner/CommandLineArgumentsProcessor.java`

コマンドライン引数を読み取り、処理結果をログへ出力します。

#### `--name`

```text
--name=Taro
```

`containsOption("name")` でオプションの有無を確認し、`getOptionValues("name")` で値を取得します。値はリストとして返されるため、次の条件を検証しています。

- 値が存在すること
- 値が1つだけであること
- 値が空白だけではないこと

`--name` が指定されなければ、名前は `"World"` になります。空の値などが指定された場合は `IllegalArgumentException` を送出し、アプリケーションの起動失敗として扱います。

#### `--verbose`

```text
--verbose
```

値を持たないフラグとして扱い、`containsOption("verbose")` の結果を `boolean` で取得します。

#### 非オプション引数

```text
input.txt
```

`getNonOptionArgs()` で、`--` で始まらない引数を取得します。現在はログへ出力するだけですが、ファイル処理などを追加する場合の入力になります。

## 5. `ApplicationArguments` の見方

次のコマンドを例にします。

```text
--name=Taro --verbose input.txt
```

| 呼び出し | 結果 |
| --- | --- |
| `containsOption("name")` | `true` |
| `getOptionValues("name")` | `["Taro"]` |
| `containsOption("verbose")` | `true` |
| `getNonOptionArgs()` | `["input.txt"]` |

Spring Boot が引数を解析してから Runner に渡すため、Runner 側で文字列を手作業で分割する必要はありません。

## 6. 実行順序と終了処理

Runner には次の順序が設定されています。

| 順序 | クラス | 処理 |
| ---: | --- | --- |
| 1 | `StartupOrderRunner` | `startup order step=1` をログ出力 |
| 2 | `CommandLineArgumentsRunner` | 引数処理をプロセッサーへ委譲 |

Runner が複数ある場合、`@Order` の値が小さいものから実行されます。Runner が1つだけの場合、通常は順序指定は不要です。

正常系では処理完了後に終了します。不正な `--name` などにより `IllegalArgumentException` が発生した場合は、`main` の `catch` 節でエラーを記録し、終了コード `1` で終了します。

## 7. テストから読み取れる仕様

### `CommandLineArgumentsProcessorTest`

場所: `src/test/java/com/example/applicationrunner/CommandLineArgumentsProcessorTest.java`

プロセッサー単体の引数処理を確認します。

- `--name=` は拒否される
- `--name=Taro --verbose input.txt` は受け付けられる
- `--name` がなければデフォルト名を使う

### `CommandLineArgumentsRunnerTest`

場所: `src/test/java/com/example/applicationrunner/CommandLineArgumentsRunnerTest.java`

Spring のコンテキストを起動して、Runner の統合的な動作を確認します。

- `CommandLineArgumentsProcessor.process` が1回だけ呼ばれる
- Runner の一覧が `StartupOrderRunner`、`CommandLineArgumentsRunner` の順になっている

`@SpringBootTest(args = ...)` により、テスト起動時のコマンドライン引数を再現しています。`@DirtiesContext` はテストメソッドごとにコンテキストを初期化し直し、Runner の実行回数が別テストの影響を受けないようにしています。

## 8. 動作確認コマンド

Java 25 を用意したうえで、プロジェクトのルートから実行します。

正常系:

```powershell
.\mvnw.cmd spring-boot:run "-Dspring-boot.run.arguments=--name=Taro --verbose input.txt"
```

`name=Taro`、`verbose=true`、`nonOptionArgs=[input.txt]` を含むログが出力されます。

引数エラー:

```powershell
.\mvnw.cmd spring-boot:run "-Dspring-boot.run.arguments=--name="
```

`IllegalArgumentException` が記録され、プロセスは終了コード `1` で終了します。

テスト:

```powershell
.\mvnw.cmd clean verify
```

## 9. コードを変更するときの確認ポイント

- Runner を追加した場合、必要に応じて `@Order` と実行順序のテストを見直す
- `ApplicationArguments` の取得方法を変更した場合、オプション引数・非オプション引数の両方を確認する
- 引数を必須にする場合や許可する値を制限する場合、正常系と不正値のテストを追加する
- Runner に処理を詰め込みすぎず、処理の詳細はサービスへ委譲する
- 起動時例外を変更した場合、ログと終了コードが期待どおりか確認する
- `ApplicationRunner` の実行は `ApplicationContext` の初期化完了後であることを意識する
